The Keyboard Contract — engineering design

Compiled from brief.md (pinned above) by the studio team, onto the mecha cluster, the omnishell terminal, the sayt loop and the bayt build graph.

Overview

Six patterns from the ARIA Authoring Practices Guide, each implemented and each shown beside the two tables the guide publishes for it. Every entity takes the tab path (decision-01): nothing is published, no migration is emitted, and the whole data plane is the terminal's in-memory collections. Four of the six tables are seeded and never written again — they are the guide's text, checked in.

The load-bearing idea is that the specification is data, and coverage of it is the check. A published keyboard table is not prose about the widget; it is a finite list of rows, each of which the app can be driven through. Keystroke holds those rows verbatim, plus one column of this implementation's own reading; the contract suite drives each one, records the id it drove, and fails if a row was never driven (decision-03). The same move is made twice: every Attribute row names an element, and the aria suite asserts that element is on the page carrying what the row says.

Three of the six patterns are one shape — a set of members, one of them current, a roving tab stop on the current one — so they are one app-local component (decision-05). What the other three cost in markup is the interesting half of this compile: two of them are a single machine over a boolean and nothing else, and the sixth is that machine three times over.

Entities

Pattern — tab

The six patterns implemented here: the name a reader knows them by, the ARIA role that names the widget, and the guide's own page for it. Seeded and never written — this is a checked-in reading list, not a thing the app maintains. The gallery's table of contents and the contract page's heading are both regions over it.

Keystroke — tab

One row per line of a pattern's published keyboard table. key, when and does are the guide's, copied; the app owns only reading and departs, which is where it says what it actually did. That split is the whole point of the table being data: the citation and the claim are different columns, so a departure cannot be made to disappear by rewording the specification (decision-02).

departs has three values and each is a different kind of honesty: no is as-written; stops is a set the guide wraps at the ends and this implementation does not (decision-04); declined is an optional behaviour not taken, with the reason in the row.

Attribute — tab

The other published table: the roles, states and properties the pattern owes. probe is the app's addition and the reason this table is a check rather than a decoration — a selector naming the element the row is about, so "each tab carries aria-selected" is something a test can go and look at (decision-06). It is not rendered: a reader is owed the claim, not the way it is found.

Option — tab

The members of the patterns that have members: three tabs, three radio buttons, three options, three accordion sections. One table rather than four, because the four differ in nothing a schema can see — a member has a key, a label, a place in the order, and sometimes a body. The accordion's open lives here rather than in Flag for the same reason it is a column at all: a section's boolean belongs to the section, and putting it elsewhere would need a second key to join on (decision-07).

Choice — tab

Which member of a widget is current: one row per widget that has a current member, and one column. It is the whole of what the arrow keys, the pointer and the tab stop all write — three ways in, one column out, which is why a widget goes the same way however it was driven (decision-08). The roving tab stop reads it through a projection rather than a stored column, so the fact "this member is current" is derived at the region and never stored twice.

Flag — tab

The two standalone booleans: the disclosure's content shown, the switch on. Their values are the strings true and false rather than a boolean type, because aria-expanded and aria-checked speak that vocabulary and the column is bound straight into the attribute — one value for the semantics and the styling hook both (decision-09).

Screens

gallery — every pattern, and the tables it owes

Reads: Pattern (order pos.asc) for the table of contents; Keystroke and Attribute (filter pattern_id=eq.<id>, order pos.asc), once per section, for the two tables; Option (filter widget=eq.<id>, order pos.asc) for the members of the four patterns that have them; Choice and Flag (filter id=eq.<id>) for what each widget currently is. The sections are written out rather than rendered from a region over Pattern: six patterns are six different widgets, and a region binds one template (decision-10).

Mutations: forms and machines, no reduce. The two booleans and the three accordion sections are #Machines over one column (decision-09); every member of a rover is written by a form — the pointer submits the member's own, an arrow key submits the neighbour's, Home and End submit the pair the component writes with the set's ends in them (pick-member, move-tabstop). keep: 1 — the page is long and returning to it from a contract page should return to where the reader was.

contract — one pattern, in full

Reads: Pattern (filter id=eq.{param.id}) for the heading and the citation; Keystroke and Attribute (filter pattern_id=eq.{param.id}, order pos.asc) for the two tables in full. No widget: the gallery is where a pattern is operated, and this page is where it is read.

Mutations: none. keep: 0 — the route is parametrised, so a held instance would accumulate one screen per pattern ever opened. strip: false — it is reached from a section, never from everywhere.

Invariants & test pairs

Every row of every published keystroke table is driven by a check that names it. The contract suite records the id of each row it drives and compares the set at the end: output.driven == input.rows && output.undriven == []. A row nobody drove is a line of the specification this app has not answered, and the run says which one rather than passing quietly.

Every element a published attribute row names is on the page carrying what the row says: output.missing == [] && output.checked == input.rows. A role row asserts the element exists and wears that role; an aria- row asserts every element the probe matches carries the attribute. This is the second table graded the same way as the first.

A tab list, a radio group and a listbox are each exactly one stop in the page's tab sequence, and the stop is on the current member: output.tabbable.all(n, n == 1) && output.stopIsCurrent. Two members in the tab order is a tab sequence decided by document order rather than by the column, which is the failure the terminal owning the tab order exists to make unrepresentable.

The arrows move the tab and activate it in one gesture, Home and End reach the ends, and exactly one tab is selected throughout: output.value == "none" && output.selectedCount == 1 && output.panelShown == output.value.

The arrows move and check together and Space checks the button with focus, with exactly one button checked at every point: output.checkedCount == 1 && output.value == "brief".

The arrows move and select, Home and End reach the ends, and exactly one option is selected: output.value == "dom" && output.selectedCount == 1.

An arrow at the end of a set names the member it is already on, so the write is a no-op and the tab list and the radio group stop where the guide would have them wrap: output.value == input.at && output.rowsMarkedStops == 4. The second half is the one that matters — the behaviour is a stated departure, so the number of rows wearing that mark is itself an assertion (decision-04).

The disclosure toggles on Enter and on Space and says which state it is in: output.afterEnter == "true" && output.afterSpace == "false" && output.expandedMatches. Neither key is listened for: the control is a button and the platform activates it, which is what makes this row cheap to satisfy and worth stating anyway.

The switch toggles with Space and carries its role and state: output.on == "true" && output.role == "switch" && output.checked == output.on. The last conjunct is the point — the attribute is the column, so they cannot disagree.

The sections open and close independently and more than one may stand open: output.open == 2 && output.expanded == output.open.

Every pattern is on the gallery with its live widget and both of its tables: output.sections == input.patterns && output.keyTables == input.patterns && output.attrTables == input.patterns.

A pattern's contract page shows that pattern's rows and no other's: output.keystrokes == 5 && output.attributes == 6 && output.otherPatterns == 0.

Both appearances render, every target is at least a thumb wide, and nothing animates: output.smallestTarget >= input.minSize && output.animations == 0. A page about keyboard operation must not move under the caret.

Decisions

01 — everything is tab, and four of the six tables are seeded. Nothing here is a reader's data: four tables are the guide's text checked in, and the two that change are which member is current and whether a boolean is on. Both die with the tab and should — a specimen sheet that remembered where you left it would be remembering the wrong thing. No migration, no policy, no publication, no pipeline.

02 — the citation and the claim are different columns. does is the guide's wording and nothing in this repository may edit it; reading is what this implementation actually does. Keeping them apart is what makes a departure impossible to hide: rewording the specification to match the code would be a diff on a column that is supposed to be a quotation, and it would be visible as one.

03 — coverage of the table is the check. The contract suite drives each keystroke row and records the id it drove; the last case asserts the driven set equals the seeded set. It is the same shape as the acceptance-coverage lint one rung up, and it exists for the same reason: a specification with rows nobody exercised is a specification the app has not answered, and nothing else in the run would say so.

04 — the ends do not wrap, and that is a platform limit, stated. The guide specifies that a tab list and a radio group wrap from the last member to the first. The read tier's projection answers next and prev — a row's neighbours — and an end names itself, deliberately, because wrapping is a per-pattern decision the read tier declines to take. There is no way to express "the first member" from the last member's row: that is a fact about the set, and a projection answers about a row. Home and End work only because the member list is compile-time data, so the component can write the two ends in as literals; an app whose members were a reader's rows could not do even that. Four rows are marked stops and the suite counts them.

05 — three patterns are one app-local component. Tabs, radio groups and single-select listboxes differ in two role names, one state attribute and whether they carry panels; they do not differ in a single mechanic. w3caria--rover is the shape, and the three instances are the differences. The alternative — three copies — is the failure the component tier exists to prevent, and on a page whose whole subject is behaviour, three copies would drift in exactly the behaviour being demonstrated.

06 — the attribute table carries a selector nobody reads. probe is the app's addition to the guide's table and it is not rendered. It is what turns "each tab carries aria-selected" from a sentence into something a check can go and look at. A table of claims with no handle on the page is a table that goes stale the first time the markup moves.

07 — the accordion's boolean is a column on the member. The disclosure and the switch keep theirs in Flag because they are not members of anything. A section's open state belongs to the section, and putting it in Flag would need a key to join on that the section already is.

08 — one column, three ways to write it. A pointer submits the member's own form, an arrow key submits the neighbour's, and the tab stop reads the same column back. All three are ordinary writes to Choice, so a widget cannot be in a state one input modality can reach and another cannot — which is the bug this whole app is about.

09 — the state name is the ARIA value. The machines' states are "true" and "false", because aria-expanded and aria-checked speak that vocabulary and one column then binds both the semantics and the styling hook. A second spelling of the same fact is a second thing to keep in step, and on this page it would be the thing being demonstrated.

10 — the six sections are written out, not rendered from a region. A region binds one template and the six widgets are six different shapes. The tables inside each section are regions, and the section frame around them is repeated markup a CUE definition generates — which is the honest split: what varies is a widget, what repeats is a frame.

11 — nothing animates. A height transition on a disclosure or an accordion panel is what makes an arrow key feel unresponsive, and it moves a target while a reader is travelling to it. There is nothing here for prefers-reduced-motion to collapse, which is the only honest way to satisfy that check on a page like this.

12 — escape hatches: none. No container, no WASM unit, no vendored component, no external endpoint, and — unusually for this tree — no Jessie either. Every behaviour here is a machine, a form or a projection. That is the finding worth carrying: six APG patterns and not one line of app code.

Reviews

backend — the data plane

Verdict: signed.

  • Six tables, one tier, no server, and four of them immutable after seeding. That is the right shape for a document that happens to be executable.
  • Pushed back on Attribute's probe column as "test data in the schema". Withdrew it: the row is a claim about a specific element, and a claim with no way to find its subject is not checkable. The column IS the claim's object.
  • One table for the members of four different widgets is right. They differ in nothing a schema can see, and four tables would have made the rover component take a table name as a parameter for no gain.
  • Open, and accepted: Option.open is meaningless for three of the four widgets, where it is seeded false and nothing reads it. A column that applies to one member set is the cost of one table for four.

frontend — the assembly

Verdict: signed.

  • Three patterns, one component, and the component's parameters are exactly the differences — two role names, a state attribute, whether there are panels, and which keys move where. That last one is written per instance rather than defaulted, which is right: which arrows a pattern answers to is the pattern.
  • The gesture forms are the part worth reading twice. An arrow key names a form; the form carries the neighbour the projection computed. Nothing imperative moves anything, and the same write happens whether the reader used a key or a pointer.
  • Home and End are the component's own literals because the projection cannot name a set's ends. Flagged as a limit rather than hidden as a helper — see decision-04.
  • Each accordion section is a nested singleton region over its own row so it can carry its own machine. That is the pattern to reuse whenever N independent booleans share one list.

designer — the identity

Verdict: signed.

  • Specimen Sheet is the right restraint. Every other app in this tree is designed to be looked at; this one is operated with the eyes closed and then read by someone checking the result, and neither audience wants a mood.
  • The well is the whole visual system: inside it you are operating something, outside it you are reading about it. One tinted surface, one hairline, and no other container anywhere on the page.
  • The focus ring is the design, and it is never removed for any input modality. Held the line on that against a "hide it for mouse users" suggestion: on this page a suppressed ring is a defect, not a preference.
  • A departure is marked in the attention colour and never in the danger one. A stated choice coloured as an error is a lie about the choice.
  • The checked and selected marks are text — a bullet, a tick — and not colour alone. On this page of all pages, a state only a sighted reader can perceive would be the joke telling itself.

ux — the felt experience

Verdict: signed, with one carried concern.

  • The page reads in the order it is operated: what the widget is, the widget, then what it owes. A reader who cannot see the widget still gets the sentence before the table.
  • Nothing animates, and that is a felt decision rather than a lazy one: an expanding panel under a caret makes an arrow key feel broken, and this page has more arrow keys than any other in the tree.
  • Carried concern: the ends not wrapping is correct-as-stated and still surprising in use. A reader pressing Right at the last tab gets nothing and no feedback that nothing was possible. The mitigation is that the row says so, on the same screen, a few centimetres below — which is more than most implementations offer and less than a wrap would.
  • Asked for and got the contract page. A section's table is enough to check a claim; the whole contract in one place is what someone comparing two implementations actually needs.

qa — the evidence

Verdict: signed.

  • Two suites, both of which grade a published table rather than the app's own opinion of itself, and both of which fail on a row nobody exercised. That coverage assertion is the strongest thing here: it is what stops the tables from becoming decoration the first time a pattern is added.
  • Both run at test — they need a mounted screen and no cluster, which is the layer the loop's rule assigns them.
  • Asked whether the keystroke rows should carry a machine-readable expectation so the driver could be generated. Rejected, and I agree with the reason: a generated assertion is the app's translation of the guide checked against the app's implementation of the guide, which grades nothing. A hand-written case per row, with coverage enforced, keeps a human in the one place that needs one.
  • The tab-order case is the one I would keep if I could keep only one: two members in the tab sequence is a bug no screenshot shows and every keyboard reader hits immediately.

platform advisor — across the seams

Advisory. No gate.

  • The headline: six APG patterns, no application code. Not a handler, not a fold, not a renderer. Machines, forms, projections and data-key carried all of it. That is the interaction tier's strongest result in this tree, and it is worth measuring against what the same six patterns cost in a component library.
  • The finding: the projection cannot name a set's ends, so no row-backed widget can wrap. decision-04 has the argument. It is not an oversight — the doc that added next and prev declined wrapping on purpose, because APG makes it differently per pattern — but the consequence is now measured: two of the six patterns here are specified to wrap and neither can. A first/last clause pair would close it and would be a fact about the set, exactly as count already is.
  • Second finding, smaller: this app wanted three independent booleans in one list and had to nest a singleton region per row to get three machines. That works and it is not obvious; it is the sort of thing that belongs in the terminal's published guidance rather than being rediscovered per app.
  • Nothing was worked around. Every check is declared in the program and lands at a verb; no script a reader would have to know to run.
